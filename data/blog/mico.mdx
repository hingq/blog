# 微服务核心知识点

微服务不是某一种框架，也不是把系统拆得越小越好。它是一种架构方式：围绕业务能力划分服务，让服务拥有清晰边界，并能够独立开发、部署和演进。

当一个系统被拆成多个服务后，原来进程内的方法调用会变成网络调用，原来由一个数据库完成的事务可能跨越多个数据源，故障也会从“一个程序出错”变成“调用链中的任意节点都可能出错”。因此，学习微服务不能只学习 Spring Cloud、Dubbo 或 Kubernetes，还要理解通信、服务治理、容错、一致性、分布式协调和可观测性之间的关系。

```text
微服务体系
├── 服务边界：如何按业务能力拆分服务
├── 服务通信：HTTP、RPC、消息队列
├── 服务治理：注册发现、负载均衡、配置、网关
├── 调用可靠性：超时、重试、幂等、熔断、限流、降级
├── 数据一致性：CAP、最终一致性、分布式事务
├── 分布式协调：共识、选主、分布式锁
├── 可观测性：日志、指标、追踪
└── 运行平台：容器与 Kubernetes
```

## 一、微服务是什么

[Martin Fowler 与 James Lewis 对微服务的总结](https://martinfowler.com/articles/microservices.html)中提到，微服务架构把应用构建为一组小型服务，这些服务围绕业务能力组织，通过轻量通信机制协作，并且可以独立部署。

这里真正重要的不是“小”，而是下面几个特征：

- **业务边界清晰**：一个服务负责一组内聚的业务能力，例如订单、库存或支付。
- **独立部署**：修改一个服务时，原则上不需要同时发布所有其他服务。
- **独立运行**：服务通常运行在独立进程中，通过网络交互。
- **数据自治**：服务应通过公开接口暴露业务能力，而不是允许其他服务直接操作自己的数据表。
- **故障隔离**：单个服务失败不应必然导致整个系统不可用。

### 微服务与单体架构

单体架构把多个业务模块构建、部署在同一个应用中；微服务则把其中一部分模块变成独立部署单元。两者不是“落后”和“先进”的关系，而是对复杂度的不同组织方式。

| 维度       | 单体架构                         | 微服务架构                             |
| ---------- | -------------------------------- | -------------------------------------- |
| 部署单元   | 整个应用                         | 单个服务                               |
| 模块通信   | 进程内调用为主                   | 网络调用为主                           |
| 数据管理   | 较容易使用同一数据库和本地事务   | 强调数据边界，经常需要跨服务一致性方案 |
| 故障范围   | 一个进程内的故障可能影响整个应用 | 可以隔离故障，但也会出现级联故障       |
| 运维复杂度 | 服务数量少，部署相对直接         | 需要服务治理、监控、自动化部署等能力   |

微服务强化了模块边界和独立部署能力，但也引入了网络延迟、部分失败、数据一致性和运维成本。[Microservice Trade-Offs](https://martinfowler.com/articles/microservice-trade-offs.html)特别强调，分布式系统更难编程，远程调用更慢且随时可能失败。因此，不应仅因为系统“看起来复杂”就拆成微服务。

## 二、服务通信

服务之间需要交换请求、响应或事件。常见通信方式包括 HTTP API、RPC 和消息队列，它们并不处于完全相同的层次。

| 方式     | 核心含义           | 常见交互                        | 适用场景                 |
| -------- | ------------------ | ------------------------------- | ------------------------ |
| HTTP     | 应用层通信协议     | 请求—响应                       | 对外 API、跨平台接口     |
| RPC      | 远程过程调用模型   | 通常为请求—响应，也可以流式传输 | 内部服务调用、强类型接口 |
| 消息队列 | 通过中间件传递消息 | 异步生产—消费                   | 事件通知、解耦、削峰     |

### HTTP 与 RPC 的关系

HTTP 规定消息怎样在客户端和服务端之间传输与解释；RPC 关注的是如何调用另一个进程提供的操作。RPC 可以建立在 HTTP/2、HTTP 或自定义传输协议之上，因此不能简单写成“HTTP 和 RPC 二选一”。

以 gRPC 为例，开发者先使用接口定义语言描述服务和消息，工具再生成客户端与服务端代码。[gRPC 官方介绍](https://grpc.io/docs/what-is-grpc/)说明，Protocol Buffers 是 gRPC 默认使用的接口定义语言和消息格式；gRPC 建立在 HTTP/2 传输之上，并支持普通请求响应、客户端流、服务端流和双向流。

Apache Dubbo 同样提供 RPC 开发模型，但它不等于某一种固定协议。[Dubbo 架构文档](https://dubbo.apache.org/en/overview/what/overview/)将其能力分为 RPC 服务定义与调用、编解码、服务发现、负载均衡和流量治理等部分。

### 一次 RPC 调用发生了什么

```text
业务代码
  ↓ 调用客户端代理
序列化请求参数
  ↓
通过网络发送请求
  ↓
服务端反序列化并定位方法
  ↓
执行业务逻辑
  ↓
序列化并返回结果
```

一个 RPC 框架通常包含以下组成部分：

- **接口描述或代理**：让调用方使用接近本地方法的形式发起请求。
- **序列化**：把内存对象转换为可传输的字节序列。
- **协议**：描述方法名、参数、结果、错误和元数据的编码方式。
- **传输层**：管理连接、读写、超时和网络异常。
- **服务寻址**：找到可用的服务实例。
- **负载均衡**：从多个实例中选择一个调用目标。

“像调用本地方法一样”只描述编程体验，不代表两者语义相同。远程调用具有本地调用没有的特征：延迟更高、请求可能超时、连接可能中断，调用方也可能无法判断服务端究竟有没有执行成功。这些差异是重试、幂等和熔断存在的根本原因。

### 同步调用与异步消息

RPC 和普通 HTTP API 常用于同步调用：调用方通常需要等待结果，才能继续当前流程。

```text
订单服务 ──请求──> 库存服务
订单服务 <──结果── 库存服务
```

消息队列把消息的生产和消费分开：生产者把事件写入消息系统后，消费者可以稍后处理。

```text
订单服务 ──OrderCreated──> 消息队列
                              ├──> 库存服务
                              └──> 积分服务
```

异步消息常用于：

- 降低生产者与消费者之间的直接依赖；
- 把非即时任务移出主请求链路；
- 缓冲短时间流量高峰；
- 传播业务事件，推动多个服务最终达到一致状态。

异步不等于天然可靠。系统仍要处理消息重复、乱序、积压、消费失败和无法永久投递等问题。业务消费者通常要具备幂等能力，并根据业务要求设计确认、重试和死信处理策略。

## 三、服务治理

当服务只有一个固定实例时，调用方可以直接保存它的地址。当实例会动态扩缩容、重启或迁移时，固定地址就不再可靠。服务治理负责管理这些动态变化。

### 服务注册与服务发现

服务注册是服务实例报告自身地址和元数据的过程；服务发现是调用方获得可用实例列表的过程。

```text
服务提供者 ──注册、续约──> 注册中心
                              ↑
服务消费者 ──查询、订阅──────┘
      │
      └──选择实例并发起调用──> 服务提供者
```

一条常见流程是：

1. 服务实例启动并注册自己的地址。
2. 实例通过心跳、租约或会话证明自己仍然存活。
3. 消费者查询并缓存可用实例列表。
4. 实例上下线时，消费者通过订阅事件或定期查询更新缓存。
5. 消费者或中间代理从可用实例中选择一个目标。

注册中心记录的“实例存在”不一定等于“业务完全健康”。健康检查还需要区分：

- **存活检查**：进程是否仍在运行；
- **就绪检查**：实例是否已经准备好接收流量；
- **依赖检查**：数据库等下游异常是否应该影响当前实例的就绪状态。

### 客户端发现与服务端发现

**客户端发现**是由调用方获取实例列表并完成负载均衡：

```text
Client ──查询注册中心──> 实例列表 ──客户端负载均衡──> Service
```

[Dubbo 服务发现](https://dubbo.apache.org/en/overview/what/core-features/service-discovery/)就是客户端发现的一个实例：提供者注册地址，消费者订阅地址变化并在本地选择调用目标。

**服务端发现**是在客户端和服务实例之间增加稳定入口或代理：

```text
Client ──> 负载均衡器或服务代理 ──> Service
```

客户端只知道稳定入口，由入口将请求转发到具体实例。[Kubernetes Service](https://kubernetes.io/docs/concepts/services-networking/service/)就是这种抽象：Service 提供稳定的访问地址，EndpointSlice 保存当前后端端点，数据平面根据这些信息把流量发送到 Pod。

### 负载均衡

负载均衡是在多个可用实例之间分配请求。常见算法包括：

- **随机**：随机选择实例，实现简单；
- **轮询**：按顺序依次选择实例；
- **加权轮询或加权随机**：让配置更高权重的实例承担更多请求；
- **最少连接或最少活跃请求**：倾向选择当前负载较低的实例；
- **一致性哈希**：相同键尽量映射到相同实例，实例变化时减少映射迁移。

负载均衡只应在健康实例之间进行。算法也不能单独保证负载均匀，因为请求耗时、实例配置、热点数据和长连接都会影响真实负载。

### 配置中心

配置中心统一保存和分发运行时配置，例如开关、阈值和服务地址。它主要解决三个问题：

- 多实例使用同一份配置来源；
- 配置变更可以被审计和回滚；
- 服务能够感知配置更新，而不必逐台修改机器。

配置中心不应成为保存所有敏感信息的默认位置。密钥通常还需要专门的权限控制、加密和轮换机制。在 Kubernetes 中，[ConfigMap](https://kubernetes.io/docs/concepts/configuration/configmap/)用于保存供其他对象使用的非机密配置数据。

### API Gateway

API Gateway 是外部客户端访问内部服务的统一入口，常见职责包括：

- 路由和协议适配；
- 身份认证与访问控制；
- 限流、审计和访问日志；
- 聚合多个内部服务的结果；
- 隐藏内部服务拓扑。

网关解决的是入口流量管理问题，注册中心解决的是服务地址发现问题，两者不能互相替代。网关也不应承载大量业务规则，否则它会成为难以演进的集中式业务层。

## 四、服务调用的可靠性

分布式系统允许一部分组件失败，而其他组件继续运行。这种“部分失败”意味着调用方必须为慢响应、暂时不可用、重复请求和持续故障设计明确策略。

### 超时

超时规定调用方最多等待多长时间。没有超时的调用可能长期占用线程、连接和内存，最终让故障从一个下游扩散到整个调用链。

超时时间不应只是一个随意的固定值。它应结合接口延迟分布、用户请求的总时间预算和下游调用层级来设置。如果最外层请求只有 1 秒预算，内部每一层都等待 1 秒，就无法保证整体在 1 秒内结束。

### 重试

重试用于处理短暂故障，例如瞬时网络抖动或某个实例刚好不可用。但重试只适合可能自行恢复、并且允许重复执行的操作。

设计重试时要明确：

- 哪些错误可以重试，例如连接失败或特定服务端错误；
- 最大尝试次数，包括首次请求还是仅计算额外重试；
- 是否采用指数退避和随机抖动，避免大量客户端同时重试；
- 是否切换实例，以及是否仍在整个请求的时间预算内。

如果每个原始请求最多发起 3 次**总尝试**，最坏情况下请求量会接近原来的 3 倍；如果定义为“首次调用后再重试 3 次”，最坏情况下则是 4 倍。调用链每一层都独立重试还可能产生乘法效应，形成重试风暴。

### 幂等

幂等表示同一操作执行一次或多次，对业务状态产生的有效结果相同。查询通常天然接近幂等，但创建订单、扣款、发放优惠券等操作通常不是。

常见做法是让调用方提供唯一请求标识：

```text
收到 requestId
  ├── 已处理：返回之前保存的结果
  └── 未处理：执行业务、保存结果，再返回
```

仅检查 requestId 是否存在还不够；“检查”和“写入业务结果”之间需要具备原子性或等价保护，否则并发请求仍可能重复执行。

### 熔断

熔断器根据一段时间内的失败率、慢调用比例等信号，暂时阻止对故障依赖的调用，从而避免持续消耗资源。

```text
Closed：正常放行请求
   │ 失败达到阈值
   ↓
Open：快速失败，不再调用下游
   │ 等待一段时间
   ↓
Half Open：放行少量探测请求
   ├── 恢复成功 → Closed
   └── 仍然失败 → Open
```

熔断保护的是调用方和整体系统，它不能修复下游服务。熔断后的请求需要明确返回错误、缓存结果或降级数据。

### 限流

限流控制一定时间内允许通过的请求量，保护服务不被突发流量或异常调用压垮。

常见算法包括固定窗口、滑动窗口、漏桶和令牌桶。令牌桶按速率补充令牌，请求获得令牌后才能通过，因此既能控制长期平均速率，也能在桶内仍有令牌时允许一定突发流量。

限流需要明确作用范围：单实例限流、单用户限流、单接口限流和全局限流解决的是不同问题。多实例本地限流不能自动得到严格的全局上限。

### 降级

降级是在依赖不可用或系统过载时，主动减少非核心能力以保留核心链路。例如推荐服务失败时返回空推荐，而不是让商品详情整体失败。

这几个机制的关系可以概括为：

| 机制 | 主要解决的问题             |
| ---- | -------------------------- |
| 超时 | 不无限等待慢调用           |
| 重试 | 恢复短暂失败               |
| 幂等 | 避免重复执行造成重复副作用 |
| 熔断 | 暂停调用持续失败的依赖     |
| 限流 | 控制进入系统的请求量       |
| 降级 | 故障或过载时保留核心能力   |

## 五、数据一致性

单体应用常利用同一个数据库事务完成多步写入。服务拆分后，订单、库存和支付可能分别拥有自己的数据库，一个本地事务无法直接覆盖所有服务，这就产生了跨服务一致性问题。

### CAP 定理

CAP 中的三个字母表示：

- **Consistency**：这里指线性一致性，即所有操作表现得像在同一时刻按单一顺序完成；
- **Availability**：每个到达非故障节点的请求最终都能收到非错误响应；
- **Partition tolerance**：即使节点之间的部分网络消息丢失，系统仍能继续满足既定保证。

[Gilbert 与 Lynch 对 CAP 的形式化证明](https://www.cs.princeton.edu/courses/archive/spr25/cos418/papers/cap.pdf)讨论的是：当网络发生分区时，系统不能同时保证上述一致性和可用性。因此，“一个系统永远只能从 C、A、P 中选择两个”是过度简化。真正需要回答的是：分区发生时，哪些操作拒绝或等待，哪些操作允许返回可能不一致的结果，以及分区恢复后怎样收敛。

把 ZooKeeper 或 etcd 简单贴成“CP 系统”只能帮助初步记忆，不能代替对具体 API 语义的理解。例如 etcd 默认读取可以提供线性一致性，但客户端也能主动请求可能读取旧值的 Serializable read；具体保证应以 [etcd API Guarantees](https://etcd.io/docs/v3.5/learning/api_guarantees/)为准。

### BASE 与最终一致性

BASE 常被展开为 Basically Available、Soft State、Eventually Consistent。它不是与 CAP 对等的数学定理，而是一组放宽即时一致性、换取系统可用性和扩展性的工程思想。[ACM Queue 的 BASE 文章](https://queue.acm.org/detail.cfm?id=1394128)将其作为 ACID 之外的一种大规模系统设计思路。

最终一致性表示：在没有新更新的前提下，各副本或各服务的状态最终会收敛。它并不保证收敛需要多久，也不自动解决冲突。因此，采用最终一致性时还要定义：

- 中间状态是否允许被用户看到；
- 消息丢失或重复时如何恢复；
- 冲突如何检测和解决；
- 长时间未收敛时如何告警与人工修复。

### 分布式事务的常见思路

假设创建订单需要完成三个步骤：

```text
订单服务：创建订单
库存服务：预留库存
支付服务：完成扣款
```

任一步骤失败，都要决定前面已经成功的步骤怎样处理。常见方案包括：

- **两阶段提交（2PC）**：协调者先要求参与者准备，再统一提交或回滚。它强调统一提交结果，但参与者和协调者之间存在等待与故障恢复成本。
- **TCC**：业务显式提供 Try、Confirm、Cancel 三类操作，先预留资源，再确认或释放。控制力强，但业务改造成本高。
- **Saga**：把长事务拆成多个本地事务；后续步骤失败时，按规则执行补偿操作。补偿通常是业务上的反向操作，不一定能恢复到字节级原状态。
- **事务消息或本地消息表**：先保证业务状态与待发送事件在本地可靠落库，再异步投递并由消费者幂等处理，常用于最终一致性。

不存在适用于所有场景的“最强”方案。选型取决于业务能否接受中间状态、是否允许补偿、对一致性与延迟的要求，以及故障恢复能力。

## 六、分布式协调

多个节点共同工作时，经常需要对“谁负责执行”“操作先后顺序”和“共享状态是什么”达成一致。共识算法、Leader Election 和分布式锁相互关联，但不是同一个概念。

- **共识**：多个节点对某个值或操作顺序达成一致，是复制状态机的基础。
- **Leader Election**：从多个候选节点中选出当前领导者，常用于集中协调写入。
- **分布式锁**：让多个进程在某段时间内只有一个持有者进入临界区。

分布式锁通常依赖一个具备明确一致性和故障检测语义的协调系统；Leader Election 也可以建立在这样的系统之上。共识算法则是 ZooKeeper、etcd 这类协调系统内部复制状态的基础。

### ZooKeeper

ZooKeeper 是 Apache 提供的分布式协调服务。它提供一个层次化命名空间，数据节点称为 ZNode。[ZooKeeper Programmer's Guide](https://zookeeper.apache.org/doc/current/zookeeperProgrammers.html)详细定义了数据模型、会话、临时节点和 Watch 语义。

```text
/
├── services
│   └── user-service
│       ├── instance-0001
│       └── instance-0002
└── locks
    └── order
```

常见节点属性包括：

- **持久节点**：创建后一直存在，直到被显式删除；
- **临时节点**：与客户端会话绑定，会话失效后被删除；
- **顺序节点**：ZooKeeper 在节点名后附加单调递增序号。

临时节点可以表示服务实例或锁持有者：客户端会话失效后节点会被清理。临时顺序节点可以组合出锁和选主等协调原语。

ZooKeeper Watch 用于监听节点变化。传统 Watch 是**一次性触发器**：收到事件后，如果还要监听后续变化，客户端需要再次设置 Watch。断开连接期间客户端收不到 Watch 事件，而且在重新设置监听的间隔内，同一个节点可能已经发生多次变化。因此，客户端收到通知后通常应重新读取状态，不能把每个 Watch 当成完整的变更日志。

ZooKeeper 使用原子广播协议维护副本间的一致顺序，写入由 Leader 协调，并在达到法定多数后提交。集群常使用奇数个投票节点，是因为 `2f + 1` 个节点可以容忍 `f` 个节点故障；偶数节点并非协议禁止，但通常不会比少一个节点获得更高的多数故障容忍能力。

### etcd

etcd 是一致、持久的分布式键值存储，也是 Kubernetes 保存集群状态的后端。它的核心数据模型是键值对，每次修改都会关联一个全局递增的 Revision。

```text
/services/user/instance-1 -> 10.0.0.1:8080
/services/user/instance-2 -> 10.0.0.2:8080
```

[etcd API 文档](https://etcd.io/docs/v3.7/learning/api/)中的三个核心能力是：

- **KV**：读取、写入、删除键值，并支持带条件的事务操作；
- **Watch**：从某个 Revision 开始持续接收键的修改事件；
- **Lease**：给键绑定租约，租约到期或被撤销时删除相关键。

服务可以把实例键绑定到 Lease，并持续发送 KeepAlive。实例长时间无法续约时，Lease 到期，实例键被删除，订阅该前缀的客户端会收到删除事件。

etcd 使用 [Raft](https://raft.github.io/)复制日志。Raft 把共识过程拆成 Leader Election、Log Replication 和 Safety 等部分：

```text
客户端写入
   ↓
Leader 追加日志
   ↓
复制到 Followers
   ↓
多数节点确认
   ↓
提交并应用到状态机
```

Raft 中的多数派保证任意两个多数集合至少有一个共同节点，这是已提交日志不会被另一组互不相交节点随意覆盖的重要基础。它解决的是副本如何就日志顺序达成一致，不直接等于服务发现、分布式锁或业务事务。

### ZooKeeper 与 etcd 的关系

| 知识点   | ZooKeeper                  | etcd                                      |
| -------- | -------------------------- | ----------------------------------------- |
| 数据模型 | 层次化 ZNode               | 扁平 KV，并带 Revision                    |
| 临时状态 | 会话与临时节点             | Lease 与绑定键                            |
| 变化通知 | Watch；传统 Watch 一次触发 | 可从 Revision 开始的 Watch 流             |
| 复制协议 | ZooKeeper 原子广播协议     | Raft                                      |
| 常见用途 | 协调、选主、锁、服务发现   | 配置、服务发现、协调、Kubernetes 状态存储 |

二者都能作为协调基础设施，但应用必须理解各自的会话、租约、读取一致性和监听语义，不能只因为都支持 KV 或 Watch 就认为行为完全相同。

### 分布式锁

分布式锁的目标是协调多个进程访问共享资源。以 ZooKeeper 为例，[官方 Recipes](https://zookeeper.apache.org/doc/r3.7.2/recipes.html)给出的锁思路是：每个竞争者创建临时顺序节点，序号最小者获得锁，其他竞争者监听排在自己前面的节点。

```text
/locks/order
├── lock-000001  ← 持有锁
├── lock-000002  ← 监听 lock-000001
└── lock-000003  ← 监听 lock-000002
```

锁节点与会话或租约绑定，可以减少持有者崩溃后永久不释放的问题，但这仍不代表业务一定安全。需要继续考虑：

- 持有者因长暂停而失去锁后，是否还会继续写共享资源；
- 锁是否需要可重入、公平和超时语义；
- 网络延迟下，客户端如何确认自己仍是合法持有者；
- 共享资源能否使用 fencing token 拒绝旧持有者的迟到写入。

因此，分布式锁是一套协议，不只是“写入一个带过期时间的键”。

## 七、可观测性

监控只能告诉我们预先定义的指标是否异常；可观测性更关注能否根据系统输出理解内部状态。微服务调用链更长、实例更多，因此需要关联日志、指标和追踪信号。

[OpenTelemetry Signals](https://opentelemetry.io/docs/concepts/signals/)把常用遥测信号定义为 Traces、Metrics、Logs 和 Baggage。通常所说的三类核心信号是日志、指标和追踪。

### 日志 Logs

日志记录离散事件，例如请求参数校验失败、消息消费失败或配置发生变化。日志适合回答“某个时间点发生了什么”。

在微服务中，日志至少应包含时间、服务名、实例、日志级别和请求关联标识。结构化日志比自由文本更容易查询和聚合，但日志中不应直接记录密码、令牌和敏感业务数据。

### 指标 Metrics

指标是随时间采集的数值，例如：

- 请求量和错误率；
- 延迟分位数；
- CPU、内存和连接池使用量；
- 队列积压和消费者处理速率。

指标适合回答“系统现在是否健康”和“趋势是否异常”。平均延迟可能掩盖少量极慢请求，因此服务延迟通常还需要观察 P95、P99 等分位数。

### 追踪 Traces

分布式追踪记录一个请求经过多个服务时形成的调用路径。一次 Trace 由多个 Span 组成，每个 Span 表示一个操作及其耗时、状态和上下文。

```text
Gateway       20ms
└── Order     80ms
    ├── Stock 15ms
    └── Pay   50ms
```

追踪适合回答“请求经过了哪里”和“时间消耗在哪一段”。要跨服务拼接调用链，Trace Context 必须通过 HTTP、RPC 或消息元数据继续传播。

三类信号需要互相补充：指标发现异常，追踪定位慢调用，日志查看具体错误。只部署采集工具而没有统一字段、上下文传播、采样和告警规则，并不能自动获得可观测性。

## 八、Kubernetes 与微服务

容器把应用及其运行依赖封装为可交付单元；Kubernetes 管理容器化工作负载的声明、调度和生命周期。它们经常用于运行微服务，但微服务不是必须运行在容器中，使用 Kubernetes 也不代表系统天然具备合理的服务边界和容错设计。

Kubernetes 为微服务运行提供的主要基础能力包括：

- Deployment 等工作负载对象管理副本和滚动更新；
- Service 与集群 DNS 提供稳定寻址和服务发现；
- Readiness、Liveness 和 Startup Probe 表达实例健康状态；
- ConfigMap 和 Secret 向工作负载提供配置；
- Horizontal Pod Autoscaler 根据指标调整副本数量；
- Gateway API 或 Ingress 管理进入集群的流量。

Kubernetes 控制面通过 API 对象表达期望状态，控制器不断让实际状态接近期望状态。[Kubernetes API 文档](https://kubernetes.io/docs/concepts/overview/kubernetes-api/)说明，Pod、Namespace、ConfigMap 等集群对象都通过 API 查询和修改；这些集群状态最终保存在 etcd 中。

需要区分两个层次：

```text
业务架构层：服务怎样拆分、通信、保证数据一致性
运行平台层：服务怎样部署、寻址、扩缩容和故障恢复
```

Kubernetes 主要解决运行平台问题，不能替代超时、幂等、事务边界和业务降级等应用层设计。

## 九、知识点之间的关系

把前面的内容放进一条调用链，可以看到各部分的职责：

```text
用户
  ↓
API Gateway ──认证、路由、入口限流
  ↓
订单服务 ──服务发现、负载均衡、超时、重试
  ↓ RPC
库存服务 ──幂等、熔断、降级
  ↓ Event
消息队列 ──异步解耦、最终一致性
  ↓
其他服务

注册中心或 Kubernetes Service：维护服务地址
ZooKeeper 或 etcd：提供一致状态与协调能力
日志、指标、追踪：观察整条调用链
```

可以按照下面的依赖关系学习：

1. 先理解进程、TCP、HTTP 和序列化，建立网络通信基础。
2. 再理解 RPC 与消息队列，区分同步调用和异步事件。
3. 学习服务注册、发现和负载均衡，理解动态实例如何互相找到。
4. 学习超时、重试、幂等、熔断、限流和降级，理解部分失败。
5. 学习 CAP、一致性模型和分布式事务，理解跨服务数据问题。
6. 学习共识、Raft、ZooKeeper、etcd 和分布式锁，理解协调系统的基础。
7. 最后学习日志、指标、追踪、容器和 Kubernetes，把应用设计与运行平台连接起来。

微服务知识体系的核心不是记住多少框架，而是理解一个变化：代码跨越进程和数据边界以后，通信不再可靠、状态不再天然一致、故障不再只有“成功或失败”两种结果。服务治理、容错、一致性和可观测性，都是围绕这个变化建立起来的。
